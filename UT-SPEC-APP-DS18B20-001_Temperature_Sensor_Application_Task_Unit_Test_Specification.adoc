== Purpose

This document defines the unit-level test specification for the `ds18b20_task` application module of the OrgPort S32K312 firmware:

* *ds18b20_task* — FreeRTOS application task that continuously polls the DS18B20 temperature sensor and publishes the latest reading (`orgport-app-s32k312/app/ds18b20/ds18b20_task.c` / `.h`)

`ds18b20_task.c/.h` is the only code authored for this feature by the engineer named in this document. Every other file the sensor depends on — the `drv_ds18b20` driver, `lib_onewire`, the `mw_gpio` open-drain fix, `drivers_init.c` (device configuration and `DRV_DS18B20_Init()` call), the GPIO pin table, the FreeRTOS task-registration and heap-sizing changes, and the build/IDE configuration — was authored by the team lead and is covered by its own, separately reviewed and already-executed test specification. This document does not re-test that code; it treats it as a trusted, pre-verified dependency and tests only the application-layer logic added on top of it.

The purpose is to verify that `APP_DS18B20_Task()` and `APP_DS18B20_GetLatest()` behave correctly — in isolation from the real driver and real hardware — under nominal, boundary, and fault-injection conditions.

== Scope

This specification covers white-box and black-box unit tests for the two public functions of `ds18b20_task`:

* `void APP_DS18B20_Task(void *pv_parameters)` — the FreeRTOS task entry point
* `void APP_DS18B20_GetLatest(DRV_DS18B20_Data_t *out)` — the accessor used by the rest of the firmware (workflow engine, CANopen TPDO packaging) to read the last published value

To isolate the application layer from the driver, all test cases in this specification link against a *test stub* of `DRV_DS18B20_Read()` (see <<test-environment,Test Environment>>) instead of the real `common-libs/drivers/sensors/ds18b20/drv_ds18b20.c`. The stub's correctness, and the correctness of `DRV_DS18B20_Init`/`DRV_DS18B20_Read` themselves, are out of scope here.

This specification does *not* cover:

* `drv_ds18b20` (Init/Read logic, CRC handling, 1-Wire timing) — lead's module, already tested
* `lib_onewire` — already tested
* `middleware/gpio/mw_gpio.c` (open-drain direction-switching fix) — lead's module, already tested
* `drivers_init.c` / `.h` (device configuration, `APP_DS18B20_Cfg`, the `DRV_DS18B20_Init()` startup call) — lead's module, already tested
* `app/gpio/GPIO_app_config.h` / `gpio_app_config.c` (DS18B20 pin assignment) — lead's module, already tested
* `app/os/os_app_config.c` (FreeRTOS task table registration) and `generate/include/FreeRTOSConfig.h` (heap sizing) — lead's module, already tested
* Physical sensor accuracy, 1-Wire bus timing, and CRC behaviour on real hardware — covered by the driver's own test specification. UT-APP-DS18B20-008 includes one informal cross-check against a handheld reference thermometer as corroborating evidence that the application layer is publishing live, sane driver output end-to-end; it is not a substitute for the driver spec's own calibrated ±0.5°C accuracy acceptance test and does not use a metrologically calibrated reference instrument.
* Integration behaviour between `ds18b20_task` and the workflow engine, FEM, or CANopen TPDO packaging — covered by the Integration Test Specification

|Since `APP_DS18B20_Task()` never returns (`for(;;)`), the host test harness runs it on a POSIX thread (`pthread_create`) against the stub driver, then calls `pthread_cancel()`/joins the thread after a bounded number of stub-recorded calls or a short wall-clock timeout (e.g. 100 ms), and only then inspects state via `APP_DS18B20_GetLatest()`. |Stub driver
|File `stub_drv_ds18b20.c`, providing a `DRV_DS18B20_Read()` with the same signature as the real driver, linked in place of `common-libs/drivers/sensors/ds18b20/drv_ds18b20.c`. |Dummy config
|A file-local dummy `DRV_DS18B20_Config_t` instance, defined in `test_ds18b20_task.c`, with `APP_DS18B20_Cfg` pointing at it for the duration of the test build (the real `APP_DS18B20_Cfg` and its populated contents belong to `drivers_init.c`, out of scope here — the test only needs *a* valid pointer, since the stub driver never dereferences it).

=== General Preconditions (apply to all test cases unless overridden)

. `stub_ds18b20_reset()` has been called immediately before each test case, clearing the call count, the recorded last-seen `cfg` pointer, and the queued result.
. The stub driver's queued result defaults to `ok = true`, `temp_c = 0.0f`, `valid = true` unless a test case sets a different value.
. No test case in this document links against the real `drv_ds18b20.c` — only against `stub_drv_ds18b20.c`.
. `s_latest_reading` inside `ds18b20_task.c` is at its static zero-initialised value (`temperature_c = 0.0f`, `valid = false`) at the start of any test case that does not first run the task. In practice this holds only for the *first* test case executed in the binary, since `s_latest_reading` is a file-static that persists for the life of the process; `test_ds18b20_task.c` orders `RUN_TEST()` calls accordingly (UT-APP-DS18B20-002 runs first, before any test starts the task).
. Test results are recorded in the Test Execution Report (document TER-APP-DS18B20-001) and in the Actual Results field of each test case below.

=== Pass / Fail Criteria

A test case passes when *all* expected results stated for each step are met with no deviation. Any single deviation constitutes a failure and must be recorded with an incident report reference.

[[automated-test-execution-procedure]]
=== Automated Test Execution Procedure

The automated test cases in this specification (see the *Execution* column of the Test Traceability Matrix) are all exercised by a single host-build Unity run against the stub driver. This procedure is performed once and the resulting console output is the evidence attached for every automated test case below.

. From `orgport-app-s32k312/app/ds18b20/tests/`, run `make` (or the equivalent host-build command — see note below). This compiles `ds18b20_task.c`, `stub_drv_ds18b20.c`, `test_ds18b20_task.c`, and Unity, then executes the resulting binary.
. Unity prints one line per test case in the form `test_ds18b20_task.c:<line>:test_<name>:PASS` (or `FAIL` with the assertion detail).
. Confirm the summary line at the end of the run reads `N Tests 0 Failures 0 Ignored`, where `N` matches the count of `Automated` rows in the Test Traceability Matrix below.
. Capture **one** console log of the full run.
. For each automated test case below, locate its test function name in the captured console log and confirm the line ends `PASS`.

NOTE: On this reviewer's machine, `make` itself could not be used directly — the only host compiler available was a MinGW-w64 GCC 13.1.0 toolchain bundled with the local S32DS install, and this machine's Windows Application Control policy blocks `as.exe` under that toolchain's default (`mingw32`) subdirectory. Its `mingw64` subdirectory was not blocked and was used instead, invoking the exact command line `make` itself generates (i.e. the equivalent host-build command referenced above). Contributors on a normal MSYS2/WSL/Linux/macOS setup should be able to run `make` directly per the Makefile in that directory.

== Module: ds18b20_task — Application Task

=== Overview

`ds18b20_task.c` is a thin application-layer wrapper with exactly two responsibilities:

* `APP_DS18B20_Task(void *pv_parameters)` — a FreeRTOS task entry point that loops forever, calling `DRV_DS18B20_Read(APP_DS18B20_Cfg, &s_latest_reading)` on every iteration and discarding the boolean return value.
* `APP_DS18B20_GetLatest(DRV_DS18B20_Data_t *out)` — copies `s_latest_reading` out to `*out` if `out` is non-NULL, otherwise does nothing.

All test cases below exercise this logic against the stub driver described in <<test-environment,Test Environment>>, not the real sensor or the real 1-Wire driver.

[cols="1,3", options="header"]
|===
|Field |Value

|Test ID
|UT-APP-DS18B20-004

|Requirement
|SWRS-SYS-03 (live sensor display)

|Objective
|Verify that `s_latest_reading` is overwritten on every loop iteration, so `APP_DS18B20_GetLatest()` always returns the *latest* stub result, not a value latched from the first successful read.

|*Expected Results:*| `out.temperature_c` is within ±0.001°C of `20.0f` (the second, more recent stub value) — not `10.0f`.
|*Actual Results:*| PASS. `test_getlatest_tracks_most_recent_iteration` — `test_ds18b20_task.c:229:test_getlatest_tracks_most_recent_iteration:PASS`. === Fault Handling (Known Gap)

==== UT-APP-DS18B20-007 — Task ignores a failed DRV_DS18B20_Read() call

[cols="1,3", options="header"]
|===
|Field |Value

|Test ID
|UT-APP-DS18B20-007

|Requirement
|CIOET-ORGPORT-CGD-2026-001 Rule 9 (every non-void return value must be checked; on failure call `LIB_FEM_Report()`)

|Objective
|Document and verify the current (non-conformant) behaviour of `APP_DS18B20_Task`: the return value of `DRV_DS18B20_Read()` is discarded with a `(void)` cast, and no fault is reported. When the stub returns `ok = false`, whatever it wrote into the output struct (including a stale or `valid = false` result) is copied into `s_latest_reading` exactly as with a successful call — the task does not distinguish success from failure and never calls `LIB_FEM_Report()`.

|Preconditions
|General preconditions apply.

|*Test Steps:* | 1) Configure the stub to return `ok = false`, `temp_c = 0.0f`, `valid = false` (simulating a CRC failure or no-presence condition). +
2) Start `APP_DS18B20_Task` and let it run for at least 1 stub-recorded call. +
3) Cancel/join the harness thread. +
4) Call `APP_DS18B20_GetLatest(&out)`.

|*Expected Results (current behaviour — documents a gap, not a clean pass):*| `out` is copied straight from the stub's output struct regardless of the `ok` return value (`out.valid == false` in this case, because the stub wrote `valid = false`) — the task performs no additional error handling, retry, or fault escalation. No call is made to any FEM/fault-reporting function from within `ds18b20_task.c`, because no such call exists in the source. This is a *known gap* against the coding standard — see Open Items OI-004 for the required fix (check the return value; on `false`, either force `s_latest_reading.valid = false` regardless of what the driver wrote, or escalate via a fault-reporting call).
|*Actual Results:*| PASS (i.e. the test confirms the documented current — non-conformant — behaviour occurs exactly as described; it does not indicate the gap itself is resolved). `test_task_ignores_failed_read_known_gap` — `test_ds18b20_task.c:232:test_task_ignores_failed_read_known_gap:PASS`. See `docs/Unit_test_report/UT-APP-DS18B20-001-TestEvidence_V1.0.txt`. OI-004 remains open.

=== On-Target Sanity Check

==== UT-APP-DS18B20-008 — GetLatest reflects a live reading once integrated with the real driver

[cols="1,3", options="header"]
|===
|Field |Value

|Test ID
|UT-APP-DS18B20-008

|Requirement
|SWRS-SYS-03 (live sensor display)

|Objective
|A single on-target sanity check confirming that the application-layer logic verified above (UT-APP-DS18B20-001 through 007, against the stub) also behaves correctly once linked against the real, already-tested `drv_ds18b20` and running on the real, already-tested FreeRTOS task/build wiring. This is a seam check between "our code" and "the lead's code", not a re-test of driver accuracy, 1-Wire timing, or CRC handling — all of which remain out of scope (covered by the driver's own specification).

|Preconditions

|*Test Steps:* | 1) Boot the DUT and allow `APP_DS18B20_Task` to run for at least 2 s (a few polling cycles at 12-bit resolution). +
2) Call `APP_DS18B20_GetLatest(&out)` from a debugger watch expression or a diagnostic task. +
3) Compare `out.temperature_c` informally against ambient temperature (no calibrated-reference accuracy check here — that is the driver spec's job).

|*Expected Results:*| `out.valid == true`; `out.temperature_c` is a plausible ambient value (not `0.0f`, not obviously garbage), confirming the task is correctly reading and publishing live driver output end-to-end.
|*Actual Results:*| *PASS.* Executed on target S32K312 hardware via GDB/PEMicro debugger, watch expression on `s_latest_reading` (equivalent to `APP_DS18B20_GetLatest()`, which copies this struct verbatim — already verified by UT-APP-DS18B20-001/002/003). (2) Later in the same session, after the sensor was deliberately heated: `temperature_c = 61`, `valid = true`, cross-checked against an independent handheld reference thermometer reading `60.9` (difference ≈ 0.1°C). The value changing between captures (24 → 61) also confirms the task was actively polling well past the required ≥ 2 s, not just returning a first-iteration read. See `docs/Unit_test_report/UT-REPORT-APP-DS18B20-001_...adoc` for the full record and image evidence.

NOTE: The reference-thermometer comparison is informal corroboration only, not the driver's own calibrated accuracy acceptance test (see the Scope caveat above).
